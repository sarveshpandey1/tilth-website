Meta Ads not converting? A 7-point tracking audit

When Meta Ads stop converting, the instinct is to change the creative or the audience. Half the time the ads are fine — Meta just can't see the conversions. Before you touch anything else, rule out tracking with these seven checks.

Anuja Founder, Tilth · 10+ years in performance marketing

Meta optimises against the conversions you report back to it. If those reports are incomplete, duplicated or pointed at the wrong action, the system cannot find buyers — so it spends the budget on the wrong people, results decay, and it looks like the ads stopped working. Most of the time that is a measurement problem wearing a creative problem's costume. Run the checks in this order.

1. Is the purchase event firing — with a value?

Use Events Manager or the Pixel Helper to confirm a Purchase event fires on the real confirmation step, carrying value and currency. Meta documents both as required for Purchase, with currency as a three-letter ISO 4217 code, and requires value for any event used with value optimisation.

Two failures are common. A Purchase event sent without value and currency still records that a purchase happened — it simply cannot tell Meta, or your own reporting, what the order was worth. That weakens revenue reporting and takes value optimisation off the table, because every order looks identical in worth. Separately, an event wired to a button click rather than a completed order counts abandoned checkouts as sales, which inflates performance and teaches the system to find people who click buttons.

2. Is the Conversions API running alongside the pixel?

Browser-side collection is fragile for ordinary technical reasons. Meta's documentation points to events the pixel may lose to network connectivity issues or page loading errors, plus events that happen offline or later and that a browser tag was never going to capture at all. The Conversions API sends those server-to-server, and Meta recommends running it alongside the pixel rather than instead of it — a redundant setup — so the goal is both sources, deduplicated, not a choice between them.

One thing it is not: a way around someone's privacy choice. Server-side collection is still your collection, and it remains subject to whatever consent and data-use obligations apply to you — Meta documents data processing options such as Limited Data Use for exactly that reason, and expects the advertiser to get this right rather than treating the server path as unrestricted. Use the Conversions API to stop losing events you are entitled to measure, not to re-collect events from people who declined.

3. Are the two sources actually deduplicated?

This is where reported performance most often becomes fiction. Meta's recommended method matches on event identity: the pixel's eventID must equal the Conversions API's event_id, and the pixel's event name must equal the server event_name. Deduplication applies to events received within 48 hours of the first event carrying that ID, and where a server and browser event arrive within about five minutes of each other Meta favours the browser event.

There is a second method using event_name with fbp and/or external_id, but it is weaker by design: it generally only works browser-first, and a server event is not discarded if no matching browser event arrived in the previous 48 hours. If you are sending the same order through both paths, send a shared event ID. Events Manager reports a deduplication rate and warns when it is too low — check it rather than assuming.

4. Is your event match quality good enough to act on?

Server events carry customer information parameters that let Meta match an event to an account, and Events Manager scores that as Event Match Quality on a 1 to 10 scale. Meta typically recommends aiming for 6.0 or higher. Sending the client IP address and user agent with every server event is specifically called out as helping matching; include the country even when every customer is in one country, and include a country code on phone numbers or they will not match.

Mind the hashing rules, because getting them backwards silently destroys matching: contact fields such as email, phone and name must be hashed, while IP address, user agent, fbc and fbp must not be. One more trap worth knowing — an event_time more than seven days old causes Meta to reject the entire request, so a backfill with stale timestamps can fail in full rather than in part.

An algorithm optimising on bad data does not fail loudly. It quietly spends your money on the wrong people.

5. Is your domain verified and your event configuration deliberate?

Aggregated Event Measurement is Meta's protocol for measuring web and app events from people on iOS 14 and later, with identifiers removed and data aggregated before it is used. Events sent through the Conversions API may also be processed within its limits, so this is not a browser-only concern. Practically: verify your domain, then open your web event configuration and look at which events are present and how they are prioritised rather than trusting whatever was set up when the pixel was installed. Meta publishes the current slot and priority rules in Events Manager for your own domain — read them there, because the limits have changed before and the number you remember may be out of date.

6. Are you optimising for the right event?

If a campaign optimises for Add to Cart or Lead because those fire more often and make the dashboard look healthier, Meta will buy carts and leads — not customers. Optimise toward the event that represents revenue, and accept the smaller, truer number. The exception is genuine volume starvation: if the revenue event fires too rarely for the system to learn from, fix the funnel or widen the offer rather than quietly optimising for a cheaper action and calling it growth.

7. Are you comparing like with like on attribution?

Meta reports on the attribution setting applied to the campaign, which includes a view-through component that a last-click model in GA4 or your backend does not count at all. The numbers should not be expected to match exactly, and chasing the gap usually means rebuilding campaigns that were fine. Check the attribution setting on the campaign you are actually judging rather than assuming a default, pick one source as your decision-making truth, and compare periods on the same basis. If the whole picture is unclear, attribution models explained simply covers why the discrepancy is expected rather than broken.

8. Is the landing page answering the ad?

Measurement integrity tells you whether the data is real. It does not tell you whether the destination deserves the click. Check that the offer, price framing and proof on the page match the promise in the creative, that the page loads quickly on a mid-range phone, and that the next step is visible without scrolling or searching. A mismatch here looks exactly like a creative problem in the dashboard, because conversion rate falls while click-through holds.

Then look for leakage further down: a checkout that asks for an account, a form that fails validation silently, a shipping cost revealed late. These cost more conversions than most creative tests recover.

9. Only now, test creative and audience

Once the purchase event is correct and valued, the Conversions API is live and deduplicated, match quality is acceptable, you are optimising on revenue and reading attribution consistently, a drop in conversions is a real signal worth chasing. Test in that order and change one thing at a time — creative against creative, audience against audience — so the result is attributable to the change rather than to the week.

That order is the point. We run it as a diagnostic before touching campaigns in paid media, and when the measurement layer itself is the thing that needs rebuilding, as growth strategy and measurement.
